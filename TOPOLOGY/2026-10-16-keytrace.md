## Part 2 — does anything still sign for 0x02B8?

**Verdict: historical — nothing is sending from `0x02B8F2C6…`.**

Evidence (all via `/rpc` on hub `127.0.0.1:8202`, cross-checked on node2):

- Account state (hub + node2, identical): balance `35999640000` base
  units, nonce **90**. (Display scale differs between readers — the raw
  figure is what matters; the inventory's "~1000 AIT" used a different
  rendering.)
- Nonce stability: re-read ~15 min later — still `90`, mempool has no
  `0x02B8` sender.
- Sender history (`/rpc/transactions?address=…&limit=100`, filtered
  `sender == 0x02B8…`): 59 sends, nonces 31–89. The newest:
  - nonce 89, block 38368, `2026-10-07T15:45` — TRANSFER → `0x34FF…f267`
    (`0x54b547daf577…`)
  - nonce 88, block 38012, `2026-10-07T09:10` — TRANSFER → `0x2aD5…3e64`
    (the live proposer key)
  - nonce 85, `2026-10-01` — GOVERNANCE_EXECUTE (self-call)
- Nothing sent after **7 Oct** — the KR-5 rotation era. The nonces line up
  exactly: account nonce 90 = last used 89 + 1, no gap.
- Repo grep for the address outside `tests/`: only genesis/workflow
  scripts naming it as a constant
  (`deploy-integrated-blockchain-node.sh`, `workflow/0*`, `19_*`) — none
  sign; all wallet signing resolves a wallet *file*, and the custody
  inventory found no file carrying this key (hub's `default.json` for
  `0x02B8` is watch-only, no key field).

What produced the last sends: nonce 89 was a plain TRANSFER out
(near-balance drain to `0x34FF…`), nonce 88 a small TRANSFER to the new
proposer `0x2aD5…` — consistent with the key being live on-hub until the
rotation/O-7 migration era, then retired. No residual signer could be
identified, and none needs to exist: the balance is spendable-but-static
treasury.
