## Findings

1. **Single-proposer in production.** `MULTI_VALIDATOR_CONSENSUS_ENABLED=false` on both nodes. The live chain has one `PoAProposer` (hub) producing every block. `aitbc3` is a follower; its `BLOCKCHAIN_MODE` / `blockchain_mode` is `follower` and it does not run the proposer loop.

2. **A validator set is configured but not used.** `VALIDATOR_SET` is non-empty on both nodes, but the master toggle is `false`, so `PoAProposer` is constructed with `consensus=None` and falls back to `self._config.proposer_id` for every block.

3. **MultiValidatorPoA is local-key rotation only.** Inspection of `apps/blockchain-node/src/aitbc_chain/consensus/poa.py` shows:
   - `_select_proposer` calls `MultiValidatorPoA.select_proposer(block_height)` only when `self._multi_validator` is set.
   - `_collect_attestations` signs with every key in `self._validator_keys` *except* the proposer. It does **not** fetch attestations from remote validators over gossip or RPC.
   - If the selected proposer is not in the local `validator_keys`, the node logs `"Selected proposer ... is not a local key, skipping proposal"` and does not produce a block.
   - `PBFTConsensus` exists in `consensus/pbft.py` but is **not wired** into `PoAProposer` or `MultiValidatorPoA`; it is never instantiated in the block production path.

4. **`multi_validator_min_attestations` makes a two-validator set unusable by default.** `config.py` defaults the value to `2`, and the hub env sets it to `2`. `sync_validator.py` requires at least that many valid attestations in `block_metadata`. With a two-validator set, a proposer can collect at most one attestation (from the other validator), so `min_attestations=2` will reject every multi-validator block. The shop env sets it to `1`, but that only matters when the shop validates blocks it imports from the hub; if the shop itself were a proposer, the hub would still require 2.

5. **No remote attestation protocol.** For `aitbc3` to be a real second proposer while the hub validates its blocks, `aitbc3` would need to include at least 2 attestations in every block it produces. It cannot collect attestations from the hub over the network, so the only practical way to satisfy `min_attestations=2` is to give the proposer node all validator private keys — which collapses multi-validator consensus back to single-node multi-key rotation.

## Implications

- The live deployment is **single-operator single-proposer**. Block production, finality, and reorg resistance all depend on the hub node and its keys.
- `multi_validator_consensus_enabled` cannot simply be flipped on for two real nodes without either:
  - lowering `multi_validator_min_attestations` to `0` (which removes the attestation safety property), or
  - implementing a remote attestation/gossip protocol (the current PBFT module is not invoked), or
  - adding a third validator and placing all three private keys on the same node (local multi-key, not distributed).
- The `VALIDATOR_SET` and `VALIDATOR_KEYS` currently loaded on hub are only useful for the homebrew / test-harness soak described in `STATUS.md`; they are **not active** in production.

## Documentation of trust assumptions (for STATUS.md / operator runbooks)

- The chain is a **single-authority PoA** network today.
- The hub operator controls block production, mempool admission, and the `proposer_key`/`validator_keys`.
- Followers (e.g. `aitbc3`) replay blocks but do not participate in consensus; they trust the hub's blocks (subject to signature and `TRUSTED_PROPOSERS` config).
- MultiValidatorPoA + PBFT is implemented in code but **fail-closed**; enabling it is an explicit operator action that requires a non-empty `validator_set`, a working attestation model, and a soak test.
- The `multi_validator_min_attestations=2` default is documented as a safety gate, but operators with only two validators must either add more validators or lower the threshold after understanding the trade-off.

## Remaining caveats

- This is still a small two-validator set with `multi_validator_min_attestations=1`, so a single attestation is the only safety margin.
- `aitbc1` was seeded by copying the hub chain DB; ongoing production deployments need a deterministic sync or snapshot mechanism rather than manual `scp`.
- The `/rpc/gossip/ws` endpoint currently has no API-key or node-authentication layer; exposing it on the public internet is acceptable only because `multi_validator_consensus_enabled` and `VALIDATOR_SET` together gate which validators can produce, but an allowlist or mTLS should be considered before broader production exposure.
- PBFT proper is still not wired into block production; the current multi-validator flow is round-robin PoA with remote header attestations, not full PBFT consensus.

## Follow-up fixes applied during live validation

1. `WebsocketGossipBackend` reconnect/retry and ack-based delivery (`broker.py`)
   - `_ensure_connection` reopens closed sockets.
   - `ping_interval=20 / ping_timeout=10` detects dead connections quickly.
   - `publish` waits for the server echo (ack); if the ack does not arrive within 10s the message is resent on a fresh connection.
   - Per-topic `asyncio.Lock` prevents `_ensure_connection`, `_reconnect`, and `publish` from racing and creating multiple/CLOSE-WAIT sockets.
   - Exponential backoff (0.5s-30s) and duplicate-reconnect suppression.

2. `MultiValidatorPoA` refuses to produce a block without enough attestations (`poa.py`)
   - If `len(attestations) < multi_validator_min_attestations`, the proposer rolls the session back and returns `False` instead of writing an invalid block with `block_metadata=None`.
   - This fixed `aitbc1` rejecting hub block 13470 (`Multi-validator block missing block_metadata attestations`).

3. Multi-validator proposers now run `periodic_sync` (`main.py`)
   - Previously `hub` mode skipped `periodic_sync` for locally-produced chains.
   - `_should_skip_sync` now returns `False` when `multi_validator_consensus_enabled` is true, so a validator that restarts can catch up via HTTP before it is selected as proposer.
