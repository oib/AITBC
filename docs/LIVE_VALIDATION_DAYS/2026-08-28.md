# Post-heavy-load recovery (2026-08-28)

**Gitea `main` baseline:** `726834bb8`

## Issues found after another heavy-load agent

1. **`aitbc3` could not reach `hub.aitbc.bubuit.net` for RPC and marketplace, returning 502 Bad Gateway.**
   - Root cause: `nginx.service` on `hub.aitbc` was `inactive`.
   - Fix: `sudo systemctl start nginx` on `hub.aitbc`.
   - Public `https://hub.aitbc.bubuit.net/rpc/head` returned height 34 afterwards.

2. **`aitbc3` could not publish default offers; Ollama offer got `400 Bad Request`.**
   - Root cause: the provider address `0xd3d4362840AC0727EEC41570b0b69CF8313E740B` had only 1053 compute-units (from the earlier `ESCROW_RELEASE`) and the `GPU_MARKETPLACE` transaction fee is 360000 compute-units (0.01 AIT).
   - Fix: funded the provider with 100 AIT = 3,600,000,000 compute-units from the `genesis-real` wallet.
   - After restarting `aitbc-miner`, the Ollama `llama3.2:3b` default offer published with a fresh `Offer ID`: `sw_offer_20260828163331_84ec042f`.

3. **Whisper and FFmpeg default offers still fail on `aitbc3`.**
   - `aitbc-whisper.service` and `aitbc-ffmpeg.service` are `not-found` on `aitbc3`. Those services are not installed on this node. Expected, and not blocking for Ollama.

4. **`aitbc` CLI on `hub.aitbc` printed `Argument list too long`.**
   - Root cause: `/opt/aitbc/venv/bin/aitbc` had a broken shell wrapper (`exec aitbc "$@"`) that recursively spawned itself, eventually overflowing the environment/argument limit.
   - Fix: replaced it with a Python shebang entry point matching `aitbc3` and `hub2.aitbc`.

**Result:** PASS — public RPC, marketplace, miner heartbeats, and Ollama offer publication are working again.

# IPFS disk quota and service (2026-08-28)

## What was found

The `ipfs-ipfs-host` offer (`sw_offer_20260826231001_6581ab42`) showed `Memory (GB): N/A` and had no visible storage quota. The user asked whether it should have a disk-space quota or is unlimited.

## Answer

It is **not unlimited**. The Kubo IPFS configs set a hard cap:

- `/var/lib/aitbc/ipfs-daemon/config`: `StorageMax: 10GB`
- `/var/lib/aitbc/data/ipfs-island/ait-hub.aitbc.bubuit.net-island/config`: `StorageMax: 10GB` (the private-island repo used by `aitbc-island-ipfs`)

With `StorageGCWatermark: 90`, GC triggers at 90% (9 GB) to stay under 10 GB.

## What was fixed

1. `aitbc-island-ipfs.service` was not installed in `/etc/systemd/system/` and had failed earlier. I copied the unit file and started it:
   - `sudo cp /opt/aitbc/apps/ipfs/aitbc-island-ipfs.service /etc/systemd/system/`
   - `sudo systemctl enable --now aitbc-island-ipfs`
2. Verified API health: `curl -X POST http://localhost:5002/api/v0/version` returns Kubo version.
3. Updated the marketplace service DB description for `ipfs-ipfs-host` to:
   - `Host files for 1 AIT per day (shared 10 GB total storage cap, GC at 90% watermark)`

## Caveat

The marketplace `softwareservice` schema currently has no dedicated `disk_quota_gb` field. The 10 GB cap is shared across all customers and enforced by the Kubo node, not per customer. Adding a real per-customer quota would require a protocol/service change.
