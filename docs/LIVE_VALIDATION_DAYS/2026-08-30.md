## Arc #7 defects fixed (2026-08-30 evening)

**Commit:** `e9c03a721` — `fix(coordinator): fail-closed ZK gate, correct unbacked-escrow check, and refund branch fixes`

### Defect 1 — ZK gate was fail-open for unregistered models

- `_zk_required_for_payment()` in `payments.py` and `_zk_required_for()` in `miner.py` were returning `False` whenever `model_registry.get_model(model_id)` returned `None`.
- `MODEL_CIRCUITS` only has `linear-1`; real jobs name `llama3.2:3b`, so `COORDINATOR_ZK_REQUIRE=true` and per-job `zk_proof_required` were silently downgraded to "no proof needed".
- **Fix:** both functions now return the policy decision and let the prover/acceptance gate decide whether the model is supported. The gate no longer resolves the model at all, so the gate/prover `resolve_model_id(job, None)` vs `(job, result)` mismatch is gone from the release path.
- **Remaining:** production models (`llama3.2:3b`, `llama2`, etc.) still have no registered `receipt_model` circuits; jobs that require ZK will be blocked with `computation_correct=False` until circuits are added.

### Defect 2 — unbacked-escrow guard proved the wrong proposition

- Guard checked `escrow_not_found and not payment.transaction_hash`. `payment.transaction_hash` is the *release* hash, so it was true of every held escrow and false-negative for escrows whose lock tx was not yet reflected in the chain's `escrow` table.
- **Fix:** guard now uses the new `_lookup_chain_lock()` helper to query on-chain `ESCROW_LOCK` transactions by `job_id`. Only when no lock tx exists does it mark the payment as an unbacked escrow.

### Defect 3 — `escrow_state == "refunded"` branch did not deactivate the escrow

- The branch at `payments.py:623` set `is_refunded=True` and `refunded_at` but omitted `is_active=False`.
- **Fix:** added `escrow.is_active = False`.
- Also removed the dead `escrow_info.get("refund_tx_hash")` expression at `payments.py:571`.

### Defect 4 — stuck-escrow sweeper also left `is_active=True`

- **Fix:** `stuck_escrow_sweeper.py` now sets `escrow.is_active = False` when it records a refund.
- Fixed pre-existing mypy/SQLModel issues in `stuck_escrow_sweeper.py` and `miner.py` that were blocking the pre-commit `mypy-clean-apps` gate.

### 20-row refund batch investigation

- 20 `job_payments` rows flipped to `refunded` at `2026-08-30 16:28:23.228218`–`.821242` (≈ 28 ms spread), all with `refund_transaction_hash IS NULL` and matching `payment_escrows.is_refunded=1, is_active=0`.
- `journalctl -u aitbc-coordinator-api` between 16:28:00 and 16:29:30 shows **no** coordinator refund/acceptance logs at 16:28:23.
- At 16:29:29 the stuck-escrow sweeper still logged `candidates=7 refunded=0 failed=7` (404s on `/rpc/escrow/.../refund`) for jobs that are in the same 20-row set (`7a9e9523...`, `d395f2b6...`, `e2834da6...`, `ecf148dd...`), confirming the 16:28:23 batch was not produced by the sweeper and the sweeper was still retrying those rows a minute later.
- Chain `transaction` table has **no** `ESCROW_LOCK` or `ESCROW_REFUND` rows for the sampled job IDs (`1a85ca2b...`, `febb20dd...`, `7a9e9523...`, `f07f4b63...`), so the 20 rows are unbacked or not yet indexed.
- **Conclusion:** the 20-row batch is consistent with a manual `UPDATE` or one-off script, not with `PaymentService.refund_payment` or the stuck-escrow sweeper. `/tmp/reconcile_refunds.py` was run earlier in the day, but its behavior and origin should be preserved in the operator runbook, not the repo.
