### Latent finding: TEE branch gating when ZK is not required

`submit_result` in `apps/coordinator-api/src/coordinator_api/contexts/infrastructure/routers/miner.py` (around line 546) currently checks `_computation_is_correct` inside the TEE branch only when `_zk_required_for(job, payment_amount)` is `True`. Because live `COORDINATOR_ZK_REQUIRE=true`, this does not currently allow a `linear-1` TEE quote to bypass the SNARK. If `COORDINATOR_ZK_REQUIRE` is ever set to `false` and a `linear-1` job is submitted with only TEE attestation, the branch would skip the `_computation_is_correct` check and could release escrow based on TEE alone. The defensive one-line change is:

```python
# before
elif _zk_required_for(job, payment_amount) and not _computation_is_correct(receipt, job):
# after
elif not _computation_is_correct(receipt, job):
```

`_computation_is_correct` already returns `True` for `tee_attested` circuit-less models and `False` for `linear-1` with no verified SNARK, so removing the `_zk_required_for` guard hardens the TEE branch without affecting the positive path.

**Status:** patch was prepared on `hub.aitbc` and validated by the targeted pytest suite, but the pre-commit `mypy-clean-apps` gate blocked the commit with unrelated mypy errors in `apps/blockchain-node`, `apps/marketplace`, `apps/wallet`, and `cli/aitbc_cli` (see the failed `hub.aitbc` commit output). The patch was therefore reverted to keep the working tree clean. The live environment is currently protected because `COORDINATOR_ZK_REQUIRE=true`, so the latent path is not exploitable. The patch can be re-applied once the mypy baseline is cleaned or the unrelated errors are fixed.

## aitbc-blockchain-rpc graceful-shutdown hang — fixed (2026-08-31)

### Root cause

`aitbc-blockchain-rpc.service` was frequently hitting systemd's `DefaultTimeoutStopSec=90s` and had to be killed with `kill -9`. `journalctl` showed 90s gaps between `Stopping` and `Stopped` for `hub.aitbc` on 2026-08-31 11:32, 12:04, 12:07, 13:43, and 13:58.

The hang was in the `lifespan` `finally` block of `apps/blockchain-node/src/aitbc_chain/app.py`. `gossip_broker.shutdown()` called `BroadcastGossipBackend.shutdown()`, which cancelled the Redis pub/sub subscription tasks and awaited them. Each task was blocked inside `async for message in pubsub.listen()` with `socket_timeout=None`. `task.cancel()` cannot interrupt a socket read, so the task only exited when the next Redis message arrived (every ~60s for the `blocks` topic). If a stop was issued during a quiet interval, the process did not exit before the 90s systemd cutoff.

### Fix

- `apps/blockchain-node/src/aitbc_chain/gossip/broker.py`:
  - `BroadcastGossipBackend._run_subscription` now polls with `pubsub.get_message(ignore_subscribe_messages=True, timeout=0.5)` and checks `stop_event`/`CancelledError` each iteration.
  - `BroadcastGossipBackend.shutdown` sets `_running=False`, cancels each task, and awaits it with `asyncio.wait_for(..., 2.0)`. The broadcast Redis connection is closed.
  - `WebsocketGossipBackend.shutdown` wraps each topic cleanup with `asyncio.wait_for(..., 5.0)`.
  - `WebsocketGossipBackend._cleanup_websocket_unsafe` uses `ws.close(close_timeout=2.0)` and `asyncio.wait_for(task, 2.0)` for the reader task.
- `apps/blockchain-node/src/aitbc_chain/app.py`:
  - `lifespan` `finally` now wraps `proposer.stop()`, `gossip_broker.shutdown()`, and `lease_tracker.stop()` in `asyncio.wait_for` with 10s/10s/5s limits so the process always exits.
- `apps/blockchain-node/aitbc-blockchain-rpc.service`:
  - Added `TimeoutStopSec=20` and `KillMode=mixed` as a hard cap.

## Gossip transaction handler log spam — fixed (2026-08-31)

### Root cause

`aitbc-blockchain-node` was logging `[ERROR] [aitbc_chain.main] Error processing transaction from gossip: transaction.from is required` repeatedly (every ~20s) on `aitbc1`. The `process_txs` task in `apps/blockchain-node/src/aitbc_chain/main.py` treated every JSON message on the websocket-gossip `transactions` topic as a raw transaction, but the generic gossip topic also carries:

- P2P-style envelopes such as `{"type": "new_transaction", "tx": {...}}`,
- control messages such as `{"type": "ping"}` and `{"type": "pong"}`,
- block-shaped metadata that lacks a `from` field.

Each of these caused `ValueError("transaction.from is required")` from `normalize_transaction_data` and was logged at error level.

### Fix

- `apps/blockchain-node/src/aitbc_chain/main.py`:
  - `process_txs` now ignores non-dict payloads.
  - It unwraps `{"type": "new_transaction", "tx": ...}` envelopes.
  - It skips `ping`/`pong` and other non-transaction control messages.
  - It validates that the payload has a `from` field before calling `normalize_transaction_data`.
  - Invalid or non-transaction messages are logged at `debug` instead of `error`, removing the log spam.

### Validation

- `ruff check` and `ruff-format` passed.
- `mypy-clean-apps` passed for the changed file.
- Commit/push: `5f54f8cc4 fix(gossip): ignore non-transaction and P2P-enveloped messages on transaction topics` on gitea `main` from `hub.aitbc`.
