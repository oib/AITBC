- Proposer rotation for the first four PBFT blocks followed the deterministic round-robin in `MultiValidatorPoA.select_proposer`:
  - `0x241D...` (node1) at height 1800
  - `0x4364...` (aitbc3) at height 1801
  - `0x6556...` (hub2) at height 1802
  - `0xab0797...` (hub) at height 1803
  - The selected proposer for height 1804 should therefore be node1 again (`1804 % 4 == 0`).
- Node1 did produce and broadcast a block at 1804. Logs on `aitbc1` show:
  - `Proposed block` at `Aug 31 20:10:41`
  - `[BROADCAST] block=1804, topic=blocks.ait-hub.aitbc.bubuit.net, valid_subscribers=1, subscribers=1`
  - Block hash `0x7483d3d8882e44363f721f3e47ee3fafa15720c47232542c2e21b176805ce39e`
- Hub, aitbc3 and hub2 all imported that block at `20:10:41/20:10:42` via `sync_block_import` (`remote height=1804, local height=1803`, parent `0x125fd2...`).
- Immediately after the 1804 broadcast, all follower WebSocket gossip connections to `wss://hub.aitbc.bubuit.net/rpc/gossip/ws` were closed with code 1012 and reconnects were rejected with HTTP 502.
- Hub2 logs then show the consensus failure for the next block:
  - `PBFT prepare quorum timeout for key 8:0`
  - `PBFT consensus failed for block 1805 on chain ait-hub.aitbc.bubuit.net; skipping proposal`
  - Repeated `PBFT commit quorum timeout for key 8:1`
- No more blocks were produced for ~17 hours. On Sep 1 13:28:34 the single-proposer hub process started and re-mined height 1804 with hash `0xeaeed56560109d800ad8072f84c5a3894c9ada066e75a4dc6e6a04dd90de55bb` (proposer `0xab0797...`).
- State root for both the node1 orphan and the hub re-mined 1804 is `0xfab871bceffc47ef6b8b50d1a0a0c2c43e2de4ceb70e136595372e85dad9e197`, identical to the parent 1803. The blocks differed only in proposer (node1 vs hub) and timestamp/signature, not in state transition.

Conclusion: block 1804 itself was not malformed and did not cause a state divergence. The chain stalled because the PBFT prepare/commit quorum for the next block could not complete after the hub RPC WebSocket endpoint was overloaded and started returning HTTP 502. The same failure mode (HTTP 502 on the gossip WebSocket, PBFT quorum timeout) was observed directly at the later 1960 activation. Raising NGINX `worker_connections` to 4096 and moving the hub RPC to Gunicorn with four `UvicornWorker` processes resolved the capacity bottleneck and allowed PBFT to reach height 2001 with all four validators in round-robin.

## Escrow / ZkRefundSweeper: refunded semantics, dedupe, DISPUTED, and stuck-escrow decisions

### Decision: "refunded" is a ledger-only status backed by an on-chain `ESCROW_REFUND` transaction

- `refunded` is **not** an on-chain event type. The on-chain event is the `ESCROW_REFUND` transaction (or equivalent contract call), recorded in `JobPayment.refund_transaction_hash` and `PaymentEscrow.refund_tx_hash`.
- A payment may only be considered truly refunded when `refund_transaction_hash` is non-empty.
- An unbacked escrow (no on-chain `ESCROW_LOCK` was ever confirmed) can be marked `refunded` by `PaymentService.refund_payment` without a hash, but that is a ledger convenience for "no funds ever moved". For audit and sweeper consistency, the ZK refund sweeper already downgrades such rows to `failed` when no hash is present. The stuck-escrow sweeper will be updated to apply the same rule: a `refunded` result without `refund_transaction_hash` is downgraded to `failed`.
- This preserves the invariant: `status == "refunded"` implies either a real on-chain `refund_transaction_hash` or a deliberate `failed` classification if the refund could not be proven.

### Escrow dedupe (3 of 6 call sites)

- Already fixed in `v0.24.18` (`apps/blockchain-node/src/aitbc_chain/rpc/escrow_routes.py`): three call sites were using `session.get(Escrow, (job_id, chain_id))` against the single-column `job_id` primary key; they now use `session.get(Escrow, job_id)`. No further action.

### DISPUTED handling in `ZkRefundSweeper`

- Decision: `ZkRefundSweeper` must **not** refund disputed payments. Disputes are operator-resolvable and have their own grace period in `StuckEscrowSweeper` (`COORDINATOR_STUCK_ESCROW_SWEEP_DISPUTED_MIN_AGE_SECONDS`).
- The `_find_candidates` query already excludes `JobPayment.status == DISPUTED`; an explicit unit test will be added to lock this behavior.

### TEE awareness in `payments.py`

- Decision: **not required in v0.25.2**. Real SGX/SEV/TPM hardware is unavailable on live nodes; TEE is deferred to release 2.0. No TEE-specific logic is added to `payments.py`. The existing ZK and receipt verification paths remain the trust anchors.

### Stuck-escrow class

- `StuckEscrowSweeper` already handles `CANCELED`, `FAILED`, `EXPIRED` jobs and `DISPUTED` payments. It will be hardened to enforce the same `refund_transaction_hash` invariant as `ZkRefundSweeper`.
