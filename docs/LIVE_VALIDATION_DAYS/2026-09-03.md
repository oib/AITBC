## PBFT view-change liveness fix — deployment to all four validators

- Implementation commit `d3861a2eb` `fix(consensus): let a later round supersede one that produced no block`.
- Deployed tip was `a0d13df0d`, which also carried `a0d13df0d fix(trading): correct down_revision in 004_v024_exchange_payment migration` (pushed by another session) and, for `hub.aitbc`/`hub2.aitbc`, the four escrow fixes and three hermes-agent commits they were behind on.
- All four validators were on a clean working tree and fast-forwarded without conflict; every host confirmed at the same HEAD before any service was touched.
- Both services (`aitbc-blockchain-node`, `aitbc-blockchain-rpc`) were restarted on all four hosts **together**, not rolling: the per-round prepare rule changes which proposals a node will accept, so a mixed fleet can disagree about a stand-in's block.

### What the fix changes

- **A later round now supersedes a round that produced no block.** `prepare_phase` previously pinned one block hash per height across *every* round. When a proposer died between its pre-prepare and the commit quorum — the exact fault rotation exists to survive — the survivors held the dead proposer's hash for that height, and the stand-in's necessarily different hash was refused forever. The pin lives only in memory, so nothing but a restart cleared it. Same-round equivocation is still refused, and a round already left behind is still refused.
- **The round carried on a pre-prepare is adopted as the PBFT view.** What used to sit in that spot was a timer armed only by the proposer inside `pre_prepare_phase`: the node that actually went dark was never counting down, nothing read the `current_view` it bumped, and timed-out proposals were counted as rotations in `consensus_view_changes_total`. The timer and its helpers are gone.
- **`consensus_proposer_round_seconds` is derived from the heartbeat** as `max(120, 2 * max_empty_block_interval)` unless set explicitly. The old hardcoded `300` sat against a deployed `MAX_EMPTY_BLOCK_INTERVAL=60` and measured 62-72 s healthy gaps, so a dark validator cost five minutes on every height it owned.

## Host-level hub outage test

`hub.aitbc` was stopped at **08:57:03 UTC** and restored at **09:06:42 UTC** (9 min 39 s). Unlike the 2026-09-02 test, **both** `aitbc-blockchain-node` and `aitbc-blockchain-rpc` were stopped, so hub's RPC, sync and gossip surface went down with it. That was listed as untested on 2026-09-02 and is now covered.

Head at the start of the outage was 4047 (hub's own block, round 0). Hub owns heights `≡ 3 (mod 4)` at round 0, so 4051 and 4055 were the heights under test.

| 4050 | hub2 (`0x6556...`) | 08:59:12 | 0 | 61 s | |

- The chain never went more than 122 s without a block across the whole outage. Nothing stalled.
- Quorum held at exactly 3 of 3 surviving validators throughout (`required=3, prepares=3, commits=3`).
- Takeover warnings fired exactly twice, both on the stand-in: `[PROPOSE] Height 4051 has gone 1 round(s) without a block` and the same for 4055.
- **Zero** `refusing a second block at height` warnings and **zero** PBFT commit-quorum timeouts on all three survivors across the window.
- The remaining warnings were all the expected hub-unreachable ones — `502 Bad Gateway` on `/rpc/subscribe` and `/rpc/head`, and `Mesh gossip peer hub.aitbc.bubuit.net unavailable` — which is the evidence that the RPC/gossip surface really was down.

### Recovery

- Hub restarted at 09:06:42, caught up without intervention, and proposed its own round-0 slot at 4059 (09:10:47).
- All four validators converged at height **4059**, hash `0xb0b1996e07119c51`, state root `0x50e75efff2f03fb4`, identical across the mesh, back to a 4-way round-robin at 60-65 s.
- No state-root divergence and no orphan `Transaction` rows.

## Honest scope of what this proves

- **Proven live:** a validator whose whole host surface is unavailable no longer costs the network a height; the round flips in ~122 s instead of ~302 s; a 3-of-4 mesh commits normally; recovery and catch-up are clean.
- **Proven only in unit tests:** the permanent-pin fix itself. Both live outages so far stopped hub cleanly *between* blocks, so no pre-prepare was outstanding and no hash was pinned. `test_the_standin_commits_a_height_the_dead_proposer_had_prepared` covers the case where the proposer dies *after* its pre-prepare is prepared by the survivors; it fails against the pre-fix `pbft.py` and passes after.
- **Still not addressed:** rotation works by superseding a round, not by a NEW-VIEW exchange carrying prepared certificates. If a proposer dies after its pre-prepare reaches a commit quorum, that quorum still materialises no block, because only a proposer writes its own block; the stand-in's block at the next round is what actually lands. Correct in practice, but it is not the textbook protocol.
- **Inherent to n=4:** with one validator down, quorum is 3 of 3 remaining, with no slack. A second validator faltering during an outage stalls the chain. This fix does not change that.
- `MultiValidatorPoA.validate_block` still has no production callers, so the receiver-side half of the schedule enforcement described in `cb8cfbf25` remains inert; only the `handle_incoming_message` pre-prepare check is live.

## Operational notes

- `aitbc-blockchain-rpc` still ignores `SIGTERM` and is `SIGKILL`ed on every stop, leaving the unit `failed` after an explicit stop (`reset-failed` before starting again). Pre-existing, unrelated to this change.
- Block timestamps in `chain.db` are UTC; host journals are local time (UTC+2). The 2026-09-02 outage table mixes the two.

### node2 fork recovery

- Fork root cause identified: node2's divergent block 4373 was produced by
  `0x19e7e376e7c213b7e7e7e46cc70a5dd086daff2a`, an unconfigured proposer not in
  the live `VALIDATOR_SET`, with an empty `state_root` and a single transaction.
  Hub's accepted block 4373 was from `0xab0797Ae8cfF09B313c71cAb2f894B342b6e1d76`,
  had a valid `state_root`, and no transactions. This points to stale/local
  `proposer_id` or `proposer_keys` configuration on `node2` rather than a
  consensus non-determinism bug.
- New `scripts/ops/reset-follower-to-snapshot.sh` creates a consistent online
  SQLite backup on the hub and installs it on a diverged follower. After manually
  transferring the snapshot (node2 has no direct SSH access to hub), node2 was
  resynced and converged at the fleet head.
- The `reset-follower-to-genesis.sh` root cause is now fixed at the code level
  by a block version gate: `state_transition_version` in `block_metadata` lets
  followers replay old blocks under v1 rules and new blocks under v2 rules.
  `STATE_TRANSITION_V2_HEIGHT` configures the fallback threshold for unversioned
  legacy blocks (default 0 for new chains).
- **Live genesis-resync test on `node0` (2026-09-03 ~22:36):** a full reset from

  the chain was reconstructed with mixed rule sets and could not be replayed
  cleanly from genesis.
- **Fleet-wide hard fork (2026-09-03 ~22:50):** to create a clean, replayable
