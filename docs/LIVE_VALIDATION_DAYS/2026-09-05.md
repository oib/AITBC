## Attestation-path root cause — FIXED in `e549a19c4`

Investigation of the 15:29 stall converged on two defects, both fixed by the
parallel session in `e549a19c4` ("Fix the multi-validator attestation gate in
poa.py") and pinned by `apps/blockchain-node/tests/consensus/test_attestation_gate.py`
(10 tests, all green on node2):

1. **Listener gated behind block production.** `PoAProposer.start()` returned
   early on `enable_block_production=false` *before* reaching
   `_remote_attestation.start()`. node0/node1/node2 run
   `ENABLE_BLOCK_PRODUCTION=false`, so their listeners never subscribed to
   `consensus.attest_request.*` — confirmed by log counts (hub:1, hub2:1,
   node1:0, node2:0 "Subscribed to remote attestation requests"). PBFT voting
   is wired from `__init__`/`_setup_gossip_subscribers` and was unaffected —
   hence quorum reached, attestations short. The fix starts the listener
   before the early return and restructures `stop()` so it no longer leaks
   the subscription on non-producing nodes.
2. **Proposer stricter than the network.** The attestation gate rejected a
   block that carried a sufficient PBFT commit certificate, while
   `sync_validator._validate_attestations` accepts the certificate *instead
   of* the attestation list — followers would have accepted what the proposer
   dropped. The certificate now satisfies the gate via
   `_certificate_commit_count` (same distinct-sender counting as the
   verifier).

My parallel work arrived at the same root cause independently; the committed
fix supersedes a redundant local edit (which a stale sshfs mount prevented
from persisting anyway).

**Still needed before the L5 soak:** fleet must run `e549a19c4` or later,
`MULTI_VALIDATOR_CONSENSUS_ENABLED=true` on all validators, and — for actual
rotation rather than just attestation — `ENABLE_BLOCK_PRODUCTION=true` on
node1/node2 (they carry `BLOCK_PRODUCTION_CHAINS` + validator keys already).
