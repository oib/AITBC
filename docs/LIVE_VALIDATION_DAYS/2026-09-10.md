# 2026-09-10 — GPU_REGISTER / GPU_ALLOCATE cross-node visibility

## Goal

Make `GPU_REGISTER` and `GPU_ALLOCATE` signed blockchain transactions apply
deterministically on the proposer and every follower, so GPU state is visible
across all five nodes.

## Root cause

Commit `d8bccaaeb` added `GPU_REGISTER`/`GPU_ALLOCATE` transaction types and
state-transition handlers, but the parallel execution path
(`sync_block_import.py`, `poa.py`) only applied account balance/nonce deltas.
The side-effect rows in `gpu_registration`/`gpu_allocation` were silently
dropped when `PARALLEL_TX_VALIDATION=true`.

Live symptom: `hub.aitbc` returned all registered GPUs, while `node2` (and
other followers) showed only the locally-seeded `test-rtx4060ti`.

## Fix

Commit `753ad3496` on `main`:

- `pure_state_transition.compute_state_delta` returns
  `requires_sequential=True` for `GPU_REGISTER`/`GPU_ALLOCATE` (same pattern as
  `LIQUIDITY_*`).
- `sync_block_import.py` skips the parallel path when any block transaction has
  a side-effect-only type.
- `poa.py` `_process_proposal_txs` does the same for block proposal.
- Added regression tests in `apps/blockchain-node/tests/test_gpu_register_state.py`.

## Deployment

Pulled `753ad3496` to `hub.aitbc`, `node0`, `node1`, `node2`, and `hub1.aitbc`;
restarted `aitbc-blockchain-node`, `aitbc-blockchain-p2p`, and
`aitbc-blockchain-rpc` on each.

## Notes

- `gpu_registration` / `gpu_allocation` are not yet included in the state root.
  A future parallel-execution rewrite must model them explicitly in `StateDelta`
  and `apply_deltas_to_db` if GPU txs are to be executed concurrently again.
- `GPU_ALLOCATE` remains available end-to-end; the sequential state-transition
  path now guarantees all followers see allocation records.
